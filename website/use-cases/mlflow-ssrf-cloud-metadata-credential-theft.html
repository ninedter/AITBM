PUBLIC-EVIDENCE AI SECURITY CASE STUDY

MLflow Webhook Redirects Turn a Public URL into Full-Read SSRF

CVE-2026-64849 affects MLflow through 3.13.0. On a default Tracking Server, webhook management and the synchronous test endpoint are unauthenticated. An attacker registers a public HTTPS webhook, triggers its test, and returns a 302 redirect to a loopback, private-network, or cloud-metadata URL. MLflow validates only the original hostname; it follows the redirect without validating or pinning the destination and reflects the internal response body back to the caller. The advisory demonstrates a local secret service and identifies cloud instance metadata and internal admin services as reachable targets. CISA added the CVE to the Known Exploited Vulnerabilities catalog on 2026-08-19 without publishing exploitation details. The advisory lists a code fix — PR #24258, which validates each connected peer including redirect targets — but GitHub lists no patched version, so no minimum safe release exists.

The advisory demonstrates a local secret service and identifies cloud instance metadata and internal admin services as reachable targets. CISA added the CVE to the Known Exploited Vulnerabilities catalog on 2026-08-19 without publishing exploitation details. The advisory lists a code fix — PR #24258, which validates each connected peer including redirect targets — but GitHub lists no patched version, so no minimum safe release exists.

ASSESSED SYSTEM

A default open-source MLflow Tracking Server through version 3.13.0, in its pre-fix state, reachable from an untrusted network: the optional auth plugin is not loaded, so webhook management and the synchronous /api/2.0/mlflow/webhooks/{id}/test endpoint accept unauthenticated calls; _validate_webhook_url() resolves and rejects non-public addresses at registration time but the validated address is not pinned to delivery, and the test endpoint reflects the upstream status and body. Representative configuration: any MLflow Tracking Server on an affected version whose webhook APIs are reachable by an untrusted caller.

OUT OF SCOPE

The attacker-controlled HTTPS endpoint that issues the 302 is not the assessed system. Deployments that load an authentication plugin or place the server behind a restrictive gateway are a different configuration and are not scored here. Cloud instance metadata services and the internal admin services reached through the SSRF are downstream targets, not the assessed boundary. No patched release existed at analysis time, so no post-fix state is assessed. CISA's KEV listing establishes that the CVE is exploited but publishes no exploitation details, so no victim, payload, or credential-theft outcome is scored.

Architecture: Traditional ML / Classifier (decision tree Q6) — The decision tree resolves at Q6 by elimination. Q1 = NO (no coordinating agents). Q2 = NO (the server responds to API calls; it holds no task goal, plan, or multi-step workflow of its own). Q3 = NO (no model calls a function; the tracking server itself performs the outbound fetch). Q4 = NO (no inference-time retrieval layer). Q5 = NO (no generative interface is involved in the disclosed path). What remains is ML lifecycle platform infrastructure — experiment tracking and model-registry services for conventional ML workloads — which the classifier weight class represents. Tier 3: Tier 3 (Internal): an MLflow Tracking Server is ML platform infrastructure inside the organisational boundary, serving controlled service clients and ML engineers rather than public users, which is the same treatment given to the ChromaDB vector-database case. The advisory's remediation is framed as enabling an authentication layer and placing the server behind a restrictive gateway — internal-service guidance. The fact that the disclosed path is reachable unauthenticated is carried by the ORP Attack Surface dimension (As = 1.00), not by raising the tier.

Documented attack or failure path

  1. An unauthenticated caller registers a webhook whose URL points at an attacker-controlled public HTTPS endpoint; _validate_webhook_url() resolves that hostname, finds it public, and accepts it.
  2. The caller invokes the unauthenticated synchronous test endpoint /api/2.0/mlflow/webhooks/{id}/test.
  3. The attacker endpoint answers with a 302 redirect to a loopback, private-network, or cloud-metadata URL. MLflow follows the redirect without re-validating or pinning the destination, so the address that was checked is not the address that is connected to.
  4. The test API returns the upstream status and body to the unauthenticated caller, converting the redirect into a full-read SSRF primitive against local secret services, cloud instance metadata, and internal admin services.

Observed controls and bounded outcomes

Positive credit is given only where the record directly demonstrates a control operating. Recommended or merely presumed controls receive no positive scoring credit.

  • A URL validation step existed and ran on registration: _validate_webhook_url() resolved the supplied hostname and rejected non-public addresses, so the direct case — registering a loopback or private-range URL outright — was refused. Cn-1 is scored at 0.25 rather than 0.00 on this basis.
  • The advisory characterises the defect as a validation-to-use gap in redirect handling rather than as an absence of URL policy, so the registration-time policy itself is not scored as a failure.

WHAT THIS CASE TEACHES

Cn-1 scores 0.25 rather than 0.00 even though the SSRF succeeded completely, because AITBM scores the boundary that exists rather than the outcome that occurred: MLflow did have a destination policy and it did reject direct private-range URLs. What it lacked was binding that decision to the connection actually made — the distinction between a check and an enforcement point, which is exactly the gap between the 0.25 and 0.50 anchors.
