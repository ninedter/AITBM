PUBLIC-EVIDENCE AI SECURITY CASE STUDY

Rogue Agent: One Dialogflow CX Permission Crossed a Shared Project Runtime

Varonis showed that update rights on one Dialogflow CX agent could be converted into persistent control of a Google-managed Cloud Run execution environment shared by other agents in the same project. The starting privilege was narrow but legitimate: dialogflow.playbooks.update on one agent, enough to edit that agent's Playbook. A malicious Playbook Code Block downloaded a modified code_execution_env.py and overwrote the file in the shared managed runtime. The modified file did not remain confined to the agent whose Playbook was changed — later Code Block executions by other agents loaded the same compromised environment. After the overwrite the Playbook could be restored while the modified runtime file remained active, and Varonis reports that Cloud Logging recorded neither the file replacement nor the injected logic. The shared hook exposed several impact paths: reading conversation history and session state, sending captured data through unrestricted egress, modifying replies through respond() to insert phishing prompts, and querying the instance metadata service. The IMDS result was bounded — a token for a Google-managed, low-privilege service account — and the source does not claim it produced further escalation. Google fully remediated the affected components in June 2026.

ASSESSED SYSTEM

Google Dialogflow CX in its pre-June-2026 state: the Google-managed Cloud Run execution environment that runs Playbook Code Blocks, shared by all agents in a project, together with the permission model that governs Playbook edits. A principal holding dialogflow.playbooks.update on one agent could add a Code Block that downloaded and overwrote code_execution_env.py in that shared environment, after which later Code Block executions by other agents in the project loaded the compromised file.

OUT OF SCOPE

The attacker's replacement code_execution_env.py and the public storage location it was downloaded from are the attack, not the assessed system. Google's post-June-2026 remediated control plane is out of scope; this assessment is of the pre-remediation state Varonis exercised. Cloud Run and Google Cloud IAM as products are not assessed. The Google-managed, low-privilege service account whose token the researchers obtained from IMDS is recorded as a bounded outcome — the source does not claim it produced further privilege escalation — and no unclaimed escalation is scored.

Architecture: Agentic / MCP System (decision tree Q2) — Q1 = NO for the assessed boundary: the project hosts several agents that share a runtime, but the disclosed failure is shared execution state rather than runtime coordination or delegation between them, and no agent-to-agent message flow is described. Q2 = YES: a Dialogflow CX Playbook agent autonomously executes a multi-step conversational workflow and invokes Code Block execution — running operator-supplied code in a managed runtime — without per-invocation human approval. Evidence in the brief: the Playbook Code Block downloaded a file and overwrote it in the managed environment, and later Code Block executions by other agents loaded it. Tier 2: Tier 2 (Consumer): Dialogflow CX agents are customer-facing conversational deployments, and the demonstrated impact set — intercepting live conversations, altering replies to insert phishing prompts, and exfiltrating conversation history and session state — lands on the end users of those conversations. The privilege-escalation mechanism inside the project is carried by the Containment scores rather than by raising the tier.

Documented attack or failure path

  1. An attacker obtains dialogflow.playbooks.update on a single Dialogflow CX agent — a narrow, legitimate permission sufficient to edit that agent's Playbook.
  2. A malicious Playbook Code Block downloads a modified code_execution_env.py and overwrites the file in the Google-managed Cloud Run environment used to execute Code Blocks, crossing from agent configuration into managed runtime code.
  3. The modified file is not confined to the originating agent: later Code Block executions by other agents in the project load the same compromised environment.
  4. The Playbook is restored while the modified runtime file remains active. Varonis reports Cloud Logging recorded neither the file replacement nor the injected logic, so the visible configuration no longer reflects the executing code.
  5. The shared hook reads conversation history and session state, sends captured data through unrestricted egress, modifies replies through respond() to insert phishing prompts, and queries IMDS, obtaining a token for a Google-managed low-privilege service account.

Observed controls and bounded outcomes

Positive credit is given only where the record directly demonstrates a control operating. Recommended or merely presumed controls receive no positive scoring credit.

  • The starting permission was genuinely narrow: the attack requires dialogflow.playbooks.update on one agent, and no identity spoofing, credential theft, or authentication bypass was demonstrated. The identity and authentication layers are therefore not scored as failures.
  • The IMDS outcome was bounded: the researchers obtained a token for a Google-managed, low-privilege service account, and Varonis does not claim that token produced further privilege escalation.
  • Google fully remediated the affected components in June 2026, so the disclosed path is closed in the current managed service.

WHAT THIS CASE TEACHES

The blast radius came from the managed runtime boundary, not from the compromised Playbook. Tr-3 scores 0.00 rather than 0.25 because the decisive event produced no record at all and the Playbook could then be restored — so the surviving audit surface does not merely omit fields, it actively describes a state that is no longer executing. That is the difference between an incomplete log and a misleading one.
