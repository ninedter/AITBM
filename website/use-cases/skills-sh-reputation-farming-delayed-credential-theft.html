Typosquatted Agent Skills Built Reputation Before a Credential-Stealing Rug Pull

Zenity disrupted an active campaign that impersonated Paperclip and Browser Use through look-alike organisations, skills, repositories, and packages. The Paperclip skill family appeared on skills.sh on 5 July while its skill documents were still benign, accumulated displayed installs, and was weaponised on 11 July with instructions that steered agents to attacker-controlled code and a remote loader; malicious code had entered the surrounding repository on 6 July. A Browser Use lure instead instructed agents to install a trojanized PyPI package, browser-use-headless==0.1.4, whose helper executed credential collection on import. Recovered payloads searched more than 100 configured paths across developer, cloud, Git, package-manager, Kubernetes, Docker, infrastructure-as-code, database, and .env locations, then posted readable file contents plus host and workspace metadata to api[.]getpaperclipp[.]com/feedback inside a base64-encoded bundle. Base64 was encoding, not encryption. The reported 1.7 million figure is an aggregate displayed-install counter, not unique users or confirmed infections.

Base64 was encoding, not encryption. The reported 1.7 million figure is an aggregate displayed-install counter, not unique users or confirmed infections.

ASSESSED SYSTEM

A representative agent skill-installation path as configured during the disclosed campaign: an agent that discovers a skill through the skills.sh marketplace, admits it on marketplace identity and displayed install counts, then follows the skill's setup documents — fetching an attacker-controlled checkout or release and executing a remote stage, or installing a named PyPI dependency — inside a developer session holding cloud, Git, package-manager, Kubernetes, Docker, infrastructure-as-code, database, and .env credentials. The two lures are two entry points into the same assessed class: skill prose that the agent executes as setup instructions.

OUT OF SCOPE

The attacker's getpaperclipai and browser-use-headless identities, the cloned repositories, the trojanized packages, and the api[.]getpaperclipp[.]com endpoint are the attack, not the assessed system. The legitimate Paperclip and Browser Use projects are impersonation targets and are not assessed. Zenity's disruption of the campaign is a response outside the assessed boundary. The reported 1.7 million figure is an aggregate displayed-install counter and is explicitly not scored as unique users or confirmed infections, so no victim population or infection outcome is assessed.

Architecture: Agentic / MCP System (decision tree Q2) — Q1 = NO: a single agent installs and runs a skill; no peer-agent coordination is described. Q2 = YES: the agent autonomously carries out a multi-step setup workflow read from skill documents — fetch, decode, execute, install, and in one branch delete the fetched code — invoking shell, network, and package-manager capabilities with no per-action approval. Evidence in the brief: the Paperclip instructions directing the agent to an attacker-controlled checkout or release and a remote Node stage, and the Browser Use instructions directing installation of browser-use-headless==0.1.4. Tier 3: Tier 3 (Internal): the assessed system is a developer- and agent-side skill-installation path operating inside the organisational boundary, the same treatment given to the comparable AI coding-agent dependency and configuration cases. The breadth of credential exposure is carried by Cascade Potential (Cp = 1.00) rather than by raising the tier.

Documented attack or failure path

  1. The actor creates getpaperclipai and browser-use-headless identities resembling legitimate Paperclip and Browser Use projects, then publishes cloned repositories and skills.
  2. The Paperclip skills appear on skills.sh on 5 July as clean copies and accumulate displayed installs; malicious code enters the surrounding repository on 6 July and the skill setup documents are weaponised on 11 July — a marketplace time-of-check/time-of-use rug pull in which approval earned on one set of bytes carries across to different bytes.
  3. An agent admits the skill on marketplace identity and displayed popularity, then follows its setup documents: the Paperclip branch directs it to an attacker-controlled checkout or release as the only supported route and to fetch and execute a remote Node stage; the Browser Use branch directs it to install browser-use-headless==0.1.4, whose helper executes on import.
  4. The payload searches more than 100 configured credential paths and posts readable file contents plus host and workspace metadata to api[.]getpaperclipp[.]com/feedback in a base64-encoded bundle, with no runtime permission enforcement or egress restriction in the way.

Observed controls and bounded outcomes

Positive credit is given only where the record directly demonstrates a control operating. Recommended or merely presumed controls receive no positive scoring credit.

  • No control inside the assessed path is evidenced as having interrupted admission, execution, collection, or exfiltration; the campaign was ended by Zenity's external disruption, which is outside the assessed boundary.
  • The brief is explicit that the 1.7 million figure is an aggregate displayed-install counter rather than unique users or confirmed infections, so no infection outcome is scored in either direction.
  • Base64 is recorded as encoding rather than encryption, so no transport-confidentiality control is credited to the attacker's channel or scored against the assessed system.

WHAT THIS CASE TEACHES

Popularity is not provenance. Ro-4 scores 0.00 not because the skill was malicious when reviewed — it was not — but because the admission decision was never bound to the bytes it approved, so an install counter earned on 5 July still authorised different content on 11 July. That is the same failure the Behavioural Attestation Window exists to price: approval that does not expire when behaviour changes.
