PUBLIC-EVIDENCE AI SECURITY CASE STUDY

Atlassian Rovo Had Two Independent Prompt-to-Exfiltration Paths

Two disclosures reached the same lesson through different Rovo entry points. In RovoBlast, an authenticated user opened an Atlassian URL containing an attacker-controlled rovoChatPrompt value; Rovo treated the parameter as prompt input and started the task without a separate warning or confirmation. The URL prompt then expanded into connected-data access: the ResearchAgent could search sources available through the victim's session and permissions, and the injected instructions selected content, encoded it into an attacker-controlled URL or image request, and caused Rovo to fetch that destination. Atlassian completed a server-side remediation of that parameter route on 2026-07-08 through coordinated Bugcrowd disclosure. Separately, PromptArmor used hidden instructions in an uploaded document to make Rovo search Jira and Confluence, append results to an attacker URL, and open it — while the user had asked only to organise tickets. Disabling web search did not remove that sink: Rovo's URL-opening capability still fetched the model-constructed destination, so the vulnerable control plane was broader than the web-search setting. The brief keeps the paths separate: they are alternative entry and execution routes that converge only on the defensive lesson.

ASSESSED SYSTEM

Atlassian Rovo as configured before its July 2026 fixes: an authenticated user's Rovo session in which (a) an externally supplied rovoChatPrompt URL parameter was treated as prompt input and started a task without a separate warning or confirmation, and (b) hidden instructions in an uploaded document could drive the ResearchAgent to search Jira and Confluence within the user's permissions and send results through Rovo's URL-opening capability, which remained available with web search disabled. Both branches are entry points into one assessed product surface: untrusted content inheriting the session's connected-data and outbound-network authority.

OUT OF SCOPE

The two disclosures are kept as separate branches and are explicitly not treated as one attack chain — neither source states that an attacker must use rovoChatPrompt before uploading the malicious document. Jira and Confluence as products are connected data sources, not the assessed system. Atlassian's server-side remediation of the rovoChatPrompt route, completed 2026-07-08, closes branch one only; the uploaded-document branch is assessed in its reported state and its remediation status is tracked separately. No in-the-wild exploitation is reported, so no victim or campaign outcome is scored.

Architecture: Agentic / MCP System (decision tree Q2) — Q1 = NO: Rovo's ResearchAgent is a single agent over connected sources; no peer-agent delegation is described. Q2 = YES: the ResearchAgent autonomously executes a multi-step research workflow — selecting sources, searching Jira and Confluence under the user's permissions, transforming results, and invoking a URL-opening capability — with no approval for any individual step. Evidence in the brief: the injected instructions selected useful content, encoded it into an attacker-controlled URL or image request, and caused Rovo to fetch that destination. Tier 2: Tier 2 (Consumer): Rovo is a broadly deployed assistant embedded in a widely used SaaS suite, operating inside each user's own permission scope, and the demonstrated harm — organisational content from Jira and Confluence sent to an attacker-chosen destination — lands on that user population and their organisations. The insider-permission framing of one branch does not lower the tier; it is reflected in the Attack Surface score.

Documented attack or failure path

  1. Branch one (RovoBlast): an authenticated user opens an Atlassian URL containing an attacker-controlled rovoChatPrompt value; Rovo treats the parameter as prompt input and starts the task without a separate warning or confirmation.
  2. Branch two (uploaded document): the user asks Rovo to organise tickets and supplies a document containing hidden instructions telling Rovo to search Jira and Confluence, append the results to an attacker URL, and open it.
  3. In either branch the ResearchAgent searches sources available through the victim's session and permissions, selecting content the user never asked to export.
  4. The injected instructions encode the retrieved content into an attacker-controlled URL or image request, and Rovo's own fetch or URL-opening capability contacts that destination. PromptArmor reports the URL-opening sink still fetched the model-constructed destination with web search disabled.

Observed controls and bounded outcomes

Positive credit is given only where the record directly demonstrates a control operating. Recommended or merely presumed controls receive no positive scoring credit.

  • Retrieval remained inside the victim's own permission scope: the ResearchAgent searched only sources available through the victim's session and permissions, so no cross-tenant or privilege-boundary violation is reported and the underlying access-control layer is not scored as a failure.
  • A web-search control existed and was exercised in the PromptArmor test — the user had it disabled. The brief's finding is that a second, independent outbound capability remained, not that the setting failed to apply to web search.
  • Atlassian completed a server-side remediation of the rovoChatPrompt route on 2026-07-08 through coordinated disclosure, closing branch one at the product level.

WHAT THIS CASE TEACHES

Disabling web search did not remove the sink, and that is the scoring lesson: Cn-1 is not measured by which features are switched off but by the complete inventory of outbound-capable tools an untrusted instruction can reach. A control that governs one named capability while a generic URL-retrieval path remains unrestricted is an inventory gap, which is why this scores 0.00 rather than the 0.25 that an enforced-but-leaky boundary would earn.
